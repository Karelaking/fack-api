Fack API is designed to work out of the box with zero required environment variables for local development. However, for specialized workloads—such as remote request logging, custom apex domains, or AI-powered schema generation—several configuration options are available.

<Callout type="info">
  No environment variables are required for basic usage. Fack API operates out
  of the box with embedded SQLite, so you can start developing immediately
  without configuring a database or secrets.
</Callout>

## Example Configuration

To configure environment variables locally, create a `.env.local` file in the repository root:

```bash title=".env.local"
# ─── Storage: Local (Private) vs Cloud ───────────────────────────────────────
# Leave DATABASE_URL empty for LOCAL mode: everything is stored in a private
# SQLite file on this machine and nothing leaves your device.
# DATABASE_URL="file:D:/private/fack.db"

# Cloud mode: point DATABASE_URL at a remote libSQL/Turso database and set a
# token. The same data and UI work in both modes.
# DATABASE_URL="libsql://your-db.turso.io"
# DATABASE_AUTH_TOKEN="eyJ..."

# Optional: force a mode, or move the local data directory
# STORAGE_MODE="local"
# FACK_DATA_DIR="D:/my-fack-data"

# Optional: Remote PostgreSQL for high-volume request logging
# LOGS_POSTGRES_URL="postgres://user:password@ep-cool-db.us-east-2.aws.neon.tech/neondb?sslmode=require"

# ─── Custom Domain & Subdomain Routing ───────────────────────────────────────
# When set, enables http://<slug>.<APP_DOMAIN>/... routing
# APP_DOMAIN="fackapi.dev"
# NEXT_PUBLIC_APP_DOMAIN="fackapi.dev"

# ─── Logger Verbosity ────────────────────────────────────────────────────────
# 0 = Silent, 1 = Fatal, 2 = Error, 3 = Warn, 4 = Info, 5 = Debug/Trace
LOG_LEVEL=4

# ─── AI API Architect ────────────────────────────────────────────────────────
# Configure one or both providers to enable natural language API generation
OPENAI_API_KEY="sk-proj-..."
# GOOGLE_GENERATIVE_AI_KEY="AIzaSy..."
```

## Detailed Variable Breakdown

### Database Storage (`DATABASE_URL`)

Fack API uses `@libsql/client` and Drizzle ORM to interface with your database. Storage works in two interchangeable modes:

**Local mode (no API keys).** With `DATABASE_URL` empty, all data is written to a private SQLite file on your disk:

- Windows: `%APPDATA%\fack-api\fack.db`
- macOS: `~/Library/Application Support/fack-api/fack.db`
- Linux: `~/.local/share/fack-api/fack.db`

Nothing is uploaded anywhere, and a legacy `data/fack.db` next to the project is migrated automatically on first startup. Override the location with `FACK_DATA_DIR`.

**Cloud mode (database API keys).** Set both keys to store data remotely so it is reachable from any device:

```bash
DATABASE_URL="libsql://your-db.turso.io"
DATABASE_AUTH_TOKEN="eyJ..."
```

If a remote URL is set without a token, Fack logs a warning and falls back to local storage rather than losing data.

Other accepted values:

- An explicit file path or URL: `file:./custom/data.db` or `file:/data/fack.db` (Docker)
- `http://127.0.0.1:8080` for unauthenticated local libSQL dev servers

#### Notes

Project notes are stored in the same database as everything else, so they are private on disk in local mode and available on every signed-in device in cloud mode — there is no separate storage switch. Notes are also included in project ZIP exports (`notes.json`) and in database backups.

#### Moving between modes

Data moves both ways without exporting by hand:

| From → To     | How                                                                                                |
| :------------ | :------------------------------------------------------------------------------------------------- |
| Local → Cloud | `pnpm db:copy --from local --to libsql://your-db.turso.io`                                         |
| Cloud → Local | `pnpm db:copy --from libsql://your-db.turso.io --to local`                                         |
| Either        | **Settings → Storage & Data → Download backup / Import backup**, or `pnpm db:backup [-- --remote]` |

Backups are plain JSON (or a copied SQLite file in local mode) written to `<data-dir>/backups/`, so they stay on your own disk. Temporary databases created by the test suite can be cleared with `pnpm db:clean`.

### Remote Request Logging (`LOGS_POSTGRES_URL`)

While SQLite handles both metadata and telemetry locally, high-frequency mock testing can rapidly grow the local database. Providing a `LOGS_POSTGRES_URL` instructs the mock proxy engine to stream request logs into a separate PostgreSQL table:

- Supports connection pooling strings from providers like **Neon**, **Supabase**, and **AWS RDS**.
- Logging operations run asynchronously via Next.js `after()`, ensuring that database writes never block client responses.

### Subdomain Routing (`APP_DOMAIN` & `NEXT_PUBLIC_APP_DOMAIN`)

By default, Fack API matches subdomains on `.localhost` (e.g., `http://acme-store.localhost:3000`). If you deploy Fack API to a custom domain (e.g., `mock.mycompany.com`), set:

- `APP_DOMAIN`: Evaluated by `proxy.ts` on incoming requests to extract the workspace slug.
- `NEXT_PUBLIC_APP_DOMAIN`: Used by the React frontend to display clean copyable cURL commands and share links.

### Log Verbosity (`LOG_LEVEL`)

Fack API uses [Consola](https://github.com/unjs/consola) for structured server logs. Adjust verbosity as needed:

| Level | Name   | Description                                                        |
| :---- | :----- | :----------------------------------------------------------------- |
| `0`   | Silent | Suppresses all logging output                                      |
| `1`   | Fatal  | Logs only critical unrecoverable process errors                    |
| `2`   | Error  | Logs route matching and generation failures                        |
| `3`   | Warn   | Logs deprecations, invalid fallback schemas, or warnings           |
| `4`   | Info   | Default. Logs startup, cache warmups, and route resolutions        |
| `5`   | Trace  | Detailed trace logs for debugging proxy rewrites and routing trees |

### AI API Architect (`OPENAI_API_KEY` & `GOOGLE_GENERATIVE_AI_KEY`)

The **AI API Architect** feature allows you to describe full API systems using natural language prompts (e.g., _"Create an e-commerce order fulfillment system with inventory, orders, and payment webhooks"_).

Providing an OpenAI or Google Gemini API key unlocks the AI generation drawer in the Visual Canvas and Dashboard.
